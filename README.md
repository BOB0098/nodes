# 节点配置链接

> 每日自动收集的免费节点订阅链接，一键复制即用。

免费节点订阅**索引站**。GitHub Actions 每 3 小时采集一次公开订阅源，统计真实条数、实测可连率与源新鲜度，按质量排序后整理成一页。打开网页 → 复制任意一条链接 → 粘进客户端 → 更新即可。

**页面只做索引**：卡片上的链接原样指向各仓库的发布地址，不改写、不合并、不转格式。你在客户端里订阅到的，就是源作者发布的原始文件。

本仓库**不托管、不分发节点凭据**。采集器会把去重后的全量清单导出到 CI 产物（`export/`，Actions artifact，保留 1 天）供自用，但该目录已在 `.gitignore` 中，不会进入版本历史——节点 URI 里带着 uuid/password 等完整凭据，公开托管等于泄露他人的账号。`data/nodes.json` 同样经过脱敏，只保留名称／协议／地区／地址／来源，不含 URI。

## 特性

- **每 3 小时自动采集** — GitHub Actions 定时拉取全部源，自动重建页面，无需人工维护
- **采集时间写在页头** — 直接显示「数据更新于 11-24 17:54」；超过 6 小时会标红提示「已 N 小时未刷新」，不让人拿旧数字当现状
- **实测数据** — 每条源抽 24 个节点测端口可连、抽 90 个节点交给 mihomo 真握手（拿到 204 才算可用），同时探测源站 HTTP 状态；节点数按文件真实条目统计
- **新鲜度透明** — 源仓库最后提交时间单独显示，超过 30 小时自动标「可能已停更」；与作者自称的更新频率分开，以实测为准
- **按真实可用条数排序** — 卡片按「这张卡里能用几条」排；端口开着不算，必须真握手通过。国内直连不通的源固定沉底，因为它复制出来也用不了
- **跨轮记录每个节点** — 累计测了几次通了几次、六时段成功率、延迟与速度历史；「稳定」要求测过 ≥3 次且成功率 ≥80%，测过一次不算
- **四类优选榜单** — 稳定 / 低延迟 / 高速 / 综合质量，每类写明入选规则与排序依据，订阅同名分组直接读它
- **三类 15 条源** — Clash 5 条、V2Ray 6 条、sing-box 4 条，每卡附适用客户端标签；清单只有一份（`sources.yaml`），页面与采集共用，不会再出现「页面有卡、后台没数」
- **一键复制 / 扫码导入** — 复制按钮直接进剪贴板，二维码弹窗支持手机相机扫码
- **筛选开关** — 真实可用 ≥50% / 国内可直连，一键过滤
- **纯静态零后端** — GitHub Pages 免费托管，无账号、无跟踪、无后端

## 每 3 小时自动更新

`.github/workflows/daily.yml` 每 3 小时跑一次 `collector.py`（cron `17 */3 * * *`，避开整点排队；GitHub 仍可能延迟，所以页面写「约 3 小时」）：

1. 并发拉取各订阅源，统计真实条数
2. 每条源抽 24 个节点测端口可连，并测源站自身 HTTP 状态；检测阶段再抽 90 个交给 mihomo 真握手
3. 用 GitHub API 查每条源最后提交时间，超过 30 小时的标「可能已停更」
4. 重建 `index.html` 与 `data/nodes.json`（含 `data/status.json`）
5. 自动 commit 回本仓库（Pages 随之更新）

带 2 小时新鲜度闸门：cron 迟到导致重复触发时直接跳过。也可以手动触发：Actions → 节点数据更新 → Run workflow。

## 源怎么挑的

清单在 `sources.yaml`（唯一事实来源），新源必须先过 `screen.py` 四关才可能启用：

1. **试采集** — 限 12 MB，记录 HTTP 状态与体积
2. **解析** — 用与入库完全相同的解析器（Clash YAML / sing-box JSON / URI / base64）
3. **去重** — 全参数 SHA-256 指纹；地址级比对会骗人，指纹级才看得出「包含关系」
4. **真实检测** — 抽样 24 个地址做 TCP 握手，算「预计可用新增 = 真正新增 × 可连率」

硬门槛：HTTP 200、解析 ≥20 条、独立新增 ≥10%、预计可用新增 ≥250 条、30 天内有提交。

P2 的实测结果（17 个候选）：

| 候选 | 解析 | 真正新增 | 可连 | 结论 |
|---|---:|---:|---:|---|
| MatinGhanbari/v2ray-configs | 3,969 | 1,764 | 25% | ✅ 启用 |
| Surfboardv2ray/TGParse | 8,189 | 4,002 | 12% | ❌ 全是死条目 |
| NoMoreWalls | 283 | **0** | 46% | ❌ 已被尔毛子全量包含 |
| AutoMergePublicNodes | 267 | 0（83% 与 NoMoreWalls 重合） | 50% | ❌ 派生项目 |

结论很反直觉但很明确：**文件大不等于节点多，节点多不等于能用**。
详见 [`docs/P2-sources.md`](docs/P2-sources.md)。

自动发现由 `discover.py` 每周跑一次，只写 `data/candidates.json` 候选队列——
**永远不会自动把新源加进订阅**，必须人工审核后置 `enabled: true`。

每轮还会跑 `governance.py` 做来源治理（不联网，读当轮产物）：把 GitHub 主站 /
raw / 三种 jsdelivr 通道归一，识别重复仓库、镜像和同仓库不同文件；在去重**之前**
按源存地址哈希，算源间内容重合度；记录每个源近 30 轮的抓取成功率、真实可用率、
重复率、最近成功时间和连续失败次数。**新增源前 3 轮等级封顶 B**，存量源不追溯；
异常源按单轮观察 / 两轮降级 / 三轮隔离处理，隔离不是删除，恢复两轮即回正常。
首轮真值（2026-11-25）：`radarhub` 的 Clash 与 sing-box 两张卡 **283 个地址 100% 重合**——
同一批节点的两种格式，不是两个独立来源；`尔毛子·可连` 与 `尔毛子·全量` 重合 93.3%。
这类重合以前只体现在「重复率 98%」这种单源数字里，现在能点到具体是哪两张卡。
报告见 [`docs/P19-governance.md`](docs/P19-governance.md)。

## 真实可用率

前面说的「可连率」都是 TCP 握手——端口开着就算通。但端口通不等于代理能用：
一个 vmess 节点完全可能端口开着、uuid 早已失效。

每轮抽样 1,200 条节点交给 mihomo（这些协议的参考实现）真握手，通过它访问
`gstatic/generate_204`，拿到 204 才算可用。卡片上的「真实可用 21/90（23%）」就是它。

两个口径的差距是这套系统的核心发现：

| 来源 | TCP 可连 | 真实可用 |
|---|---:|---:|
| radarhub | 100% | 87% |
| anaer | 88% | **2%** |
| ALIILAPRO | 54% | **3%** |

一个源的价值是真实可用条数，不是节点总数，也不是 TCP 可连率。
详见 [`docs/P6-P8-realdetect.md`](docs/P6-P8-realdetect.md)。

## 源质量怎么评的

每轮采集后 `score.py` 按**实测数据**打分（不读 README 宣传），卡片标题旁的
字母徽章就是它：S 90–100 / A 80–89 / B 65–79 / C 50–64 / D <50。

| 维度 | 满分 | 依据 |
|---|---:|---|
| **真实可用率** | 32 | mihomo 真握手 `可用/样本`，70% 封顶 |
| **真实可用条数** | 10 | 可用条数的对数刻度，800 条封顶 |
| 样本置信 | 4 | 60 条样本以下按比例 |
| 独立新增 | 10 | 只被本源包含的指纹数，对数刻度 |
| 独立率 | 6 | 独立新增 ÷ 原始解析 |
| 新鲜度 | 10 | 源内容多久没变 |
| 稳定性 | 14 | 连续失败 + 近 6 轮真实可用率波动 |
| TCP 可连率 | 8 | 只作辅助；无真实握手样本时维度上限 27.2，TCP 抽样缺失记 13.6 |
| 合规/类型 | 6 | 有 SPDX 许可证 + 来源类型 |

两条硬上限：**没有真实握手数据 → 最高 B；样本 < 20 条 → 最高 A**。
10 条里通 9 条，和 90 条里通 81 条不是一回事。

真实可用率占 32 分、TCP 只占 8 分，是 2026-11 那轮改的。上一版把 40 分给了 TCP，
结果「端口全通、真握手 0/90」的源拿 A 级并排在第一位——评分替它背了书。

淘汰只看采集失败，不看节点质量：单轮失败标「单轮异常」→ 连续两轮降级 →
连续三轮隔离（不进优选导出，但**仍然继续采集**，恢复后自动回来）。
不允许因为一次网络故障永久删源，也不允许因为分数低就悄悄下架。

完整公式、逐源明细与扣分点见 [`docs/P4-source-quality.md`](docs/P4-source-quality.md)，
每轮采集自动重写。

## 解析与去重

一条订阅可能是 Clash YAML、sing-box JSON、URI 列表或整体 base64，三种载体都由
`nodes_parse.py` 解析成同一套模型。当前支持 VMess / VLESS / Shadowsocks / Trojan /
Hysteria2 / TUIC / SOCKS5 / AnyTLS。

**明文 HTTP 代理不入库**：流量和凭据在链路上明文可读，这类条目绝大多数还是带广告的
公开代理池。但它不会被静默丢掉——每轮被丢弃的条目会按原因写进
`data/quarantine.json`（只记协议/地址/端口，不记原文），页面上「这个源少了几百条」
因此有据可查。

去重按**全参数指纹**（协议+地址+端口+凭据+传输参数一起哈希），不是 host:port。
同一台机器上不同 uuid/不同 ws 路径的节点是不同节点，按地址去重会误杀 40%。

## 节点存活多久

`lifecycle.py` 按天记录每个指纹第一次和最近一次出现的时间，派生两个指标：
卡片上的「近 7 天新增 N」和悬浮提示里的「中位存活天数」。

前者回答「这个源还在产新节点吗」——总量大不代表还在更新，一个源连续几周零新增，
通常只是旧节点在被到处转发。45 天没再出现的指纹会从历史里清掉，隔这么久又冒出来的
按新节点算才合理。

## 节点历史与优选榜单

「这一轮能连上」和「一直靠得住」是两回事。检测每轮只抽 1,200 条 / 9,846 条，
一条节点的真实表现要跨好几轮才能看出来，所以另有一层历史：

| 文件 | 记什么 | 窗口上限（代码策略） | 当前实际已积累 |
|---|---|---|---|
| `data/node_history.json` | 每节点：首次/最近出现、最近成功、累计测几次通几次、连续成败、六时段成功率、最近 5 次延迟、最近 3 次速度 | 30 天 | 见 `history.py --report` 的天数；截至 P28 审计日全部节点 `first` 同为一天，且多数为迁移记录，**尚未形成 30 天跨轮历史** |
| `data/trend.json` | 每天一行：轮次、抽样数、可用数、P50 延迟、新增/消失、按协议分桶 | 365 天 | 截至 P28 审计日 `days` 仅 **1 天**（2026-11-25），365 是留存策略不是已有数据 |
| `data/picks.json` | 四类榜单 + 每类的入选规则与排序依据 | 每轮重写 | 每轮重写，无历史跨度 |
| `data/threshold_watch.json` | 每轮分数分布观测（分位数/各门槛条数/best 分数范围） | 7 天评估窗口 | 每轮追加一行，见 `python3 threshold_watch.py --report` 的实际天数 |

**"窗口"是上限，不是已拥有多少历史**：30 天/365 天指代码会保留多久、能算多长的曲线；
当前实际天数以文件内真实数据为准。`history.py --report`、`threshold_watch.py --report`
都按真实数据报天数，不足时页面显示"已跟踪 N 天"而不是伪造"近 7 天新增"。

**稳定不看「连续几轮成功」，看累计成功率。** 抽样率 12%，连续三轮都被抽中且都成功的
概率约 1.7‰，真正稳定的节点也拿不到这个标签。现在要求测过 ≥3 次且成功率 ≥80%，
不够样本的一律标「样本不足」——测过一次就成功不足以证明稳定。

**抽样优先覆盖测得少的节点。** 纯随机抽 8 轮只能覆盖 64%，一个节点攒到「测过 3 次」
平均要三天。同源内优先抽 `tries` 小的，前 8 轮就能把全库走一遍。

四类榜单（订阅里的同名分组直接读它，不另筛一遍）：

| 榜单 | 入选条件 | 排序 |
|---|---|---|
| 稳定 | 测过 ≥3 次、成功率 ≥80%、无连败 | 成功率 → 测试次数 → 延迟 |
| 低延迟 | 中位延迟 ≤300ms、测过 ≥2 次 | 延迟 → 成功率 |
| 高速 | 中位速度 ≥1MB/s、测过 ≥2 次 | 速度 → 成功率 |
| 综合质量 | 本轮通过、不在连败中 | 评分 → 成功率 |

没有延迟数据的不进低延迟榜（不是记 0ms 排第一），没有测速的不进高速榜。
所有排序键最后用指纹兜底，保证同样数据两次刷新顺序一致。

体积是实测的：一万条约 1.3 MB，`git gc` 后每轮增长约 35 KB，
一年约 100 MB。上限线设在单文件 2 MB / 15,000 条。

细节与验收记录见 [`docs/P18-history.md`](docs/P18-history.md)。

## 安全与回滚

外部输入全是别人仓库里的文本，所以出网统一走 `netsafe`：只允许 HTTP/HTTPS、
目标必须是公网地址（解析结果逐个比对）、每跳重定向都重查、单源 12 MB 上限、
整体 90 秒预算。日志里所有 URL 与节点 URI 都过脱敏——订阅地址的 query 常放
token，`print(e)` 一次就可能把凭据写进公开的 Actions 日志。

真实检测失败不会覆盖上一轮的有效结果：本轮可用数掉到上轮的 40% 以下时判定为
环境异常，`nodecheck.json` 保持不动，页面继续用旧数据。所有 JSON 都是原子写
（先写临时文件再 rename），中断时留下的是旧文件而不是半个 JSON。

**统一构建清单（P20）**：每轮产物全部生成后，`build_manifest.py` 会把页面、节点、
检测、评分、榜单、订阅、状态、治理、趋势共 9 个文件钉在同一个 `build_id` 上，
逐个记录 sha256、字节数、原始时间戳和统一口径的计数。发布前 `check_consistency.py`
拿它做硬校验：任何一个产物被单独改过、计数对不上、或时间戳相差超过 90 分钟，
就拦下发布——CI 里这一步没有 `continue-on-error`，失败即不 push，远端保留上一版。
这解决的是一个真实事故：页面写 `11-25 14:02`、订阅写 `2026-11-25 14:15`，旧正则
只认前者，把相差 13 分钟的两份数据报成「差 0 分钟，同一轮」。

```bash
python3 build_manifest.py --write   # 生成统一清单（CI 每轮自动执行）
python3 check_consistency.py        # 发布门禁：同一轮 + 哈希吻合才放行
python3 drill_publish.py            # 发布失败回滚演练：注入坏产物→拦下→恢复
```

订阅路径、文件名与四种格式（clash / sing-box / URI / base64）在 P20 里未改动，
旧订阅入口继续可用；manifest 只做校验，不改任何产物。

**发布门槛的其余三道（P22）**：

- **数量异常下降**：`check_consistency.py` 会拿 git HEAD 里上一版的入库条数和本轮比，
  掉到 60% 以下判为采集/解析链路故障，拦下发布——防止上游改格式或被封时把
  9846 条悄悄发成 300 条、页面还显示"正常更新"。CI 用 `fetch-depth: 0` 保证 HEAD
  是上一版；本地无 git 历史时降级为警告。演练可用 `NODES_PREV_COUNT=20000` 覆盖。
- **公开产物脱敏审计**：`audit_privacy.py` 扫 `data/*.json` 与 `index.html`，发现节点
  URI、明文凭据字段、token 或 URL 内嵌凭据就拦下发布。git 历史已核对无真令牌；
  源码 selftest 里的假 token / 文档示例不算公开数据，不纳入扫描范围。
- **失败通知**：任一关键步骤失败时，CI 用 `gh` 在仓库开一个 `ci-failure` issue（已
  存在则追加评论，不刷屏），所以"页面停在上一版"会第一时间被人发现。通知本身
  失败不影响发布结论。权限只为此增开 `issues: write`，其余仍是 `contents: write`。

一条命令复现全部发布前检查：

```bash
python3 -m pip install -r requirements.txt   # 首次需装 PyYAML
bash verify.sh                                # 核心 selftest、P24 回归、隐私/一致性门禁、发布演练、全部 workflow YAML 与页面 JS
bash verify.sh --quick                        # 跳过发布演练及扩展检查
```

数据回滚不用记 git 命令：

```bash
python3 restore.py list                 # 最近 20 次数据改动
python3 restore.py to <sha> --dry-run   # 只看会改什么
python3 restore.py to <sha>             # 恢复（当前内容自动备份）
python3 restore.py undo                 # 撤销上一次恢复
```

候选源接入额外校验内容类型：HTTP 200 但返回登录页 HTML 会被判为
「内容类型校验失败」，而不是含糊地记成「解析 0 条」。治理层与审核层都不写
`sources.yaml`——白名单只有人工能改。

细节与残余风险见 [docs/P13-security.md](docs/P13-security.md)。

## 说明

- 卡片链接均为各仓库原样发布，本项目不改写、不合并。节点库为了统计与去重会把各源解析成统一模型，但不会回写源文件。
- 条数与可连率在构建时内嵌进 `index.html`，页面本身不发请求；`data/nodes.json` 是同一份数据的结构化版本，供脚本或监控读取，页面不依赖它。
- 「源更新于」来自仓库最后一次提交时间，与作者自称的更新频率分开显示，两者不一致时以实测为准。
- 不在 GitHub 上的源（如 radarhub）拿不到提交时间，改用内容指纹：每轮采集比对内容 md5，没变就沿用上次变化时间。这类源从第二轮采集起才有数值。
- 页面顶部两个筛选开关（可连 ≥80% / 国内可直连）只改显示，不改数据。
- 免费节点随时失效，一条不通就换下一条。

## Docker 部署（自建机器）

不想依赖 GitHub Actions 的话，任意一台带 Docker 的机器都能跑同一套链路：

```bash
cp .env.example .env      # 填你的 uid/gid，`id -u` / `id -g`
docker compose run --rm collect
```

一条命令跑完「采集 → 真实握手 → 评分 → 渲染 → 生成订阅」，顺序和 CI 里一模一样。
定时执行交给宿主机的 cron：

```
17 */3 * * * cd /path/to/nodes && docker compose run --rm collect >> data/logs/cron.log 2>&1
```

几个刻意的设计：

* **核心阶段失败就停并尝试恢复旧产物**。检测、评分、治理、榜单、订阅、渲染或发布门禁任一步失败，容器都会停止，并尝试把本轮前的 `data/`、页面、报告和订阅导出恢复；不会拿旧检测结果混算新采集数据
* `data/` 是宿主机挂进去的，容器只是干活的。换机器只要把目录搬走
* mihomo 放在命名卷里，第二次跑不用再下载
* 不假设多台机器共享磁盘。想并行就在各自机器上跑，再去合并 `data/nodes.json`

评估一台云服务器能不能用，先在那台机器上跑体检：

```bash
python3 dockerprobe/probe.py run --platform 你的平台名 --json probe/x.json
```

它只回答三个问题：Docker 真的能跑吗、出网通不通、中途会不会被平台停掉。
三个都过才叫「适合日常采集」。结论和三家免费平台的实测情况见
[docs/P11-docker-platforms.md](docs/P11-docker-platforms.md)。

## 本地运行

```bash
python3 collector.py            # 采集并重建 index.html（读 sources.yaml）
python3 collector.py --render   # 不联网；汇总现有数据并更新最终 nodes.json 快照与页面
python3 nodecheck.py --speed    # mihomo 真握手 + 测速（需 curl，会自己下 mihomo）
python3 nodescore.py            # 评分、地区、标签；同时累积节点历史与日趋势
python3 governance.py           # 来源治理：重复源/重合度/逐源指标/观察期
python3 governance.py --selftest # 重复源、恶意 URL、超大响应、故障恢复四项验收
python3 picks.py                # 四类优选榜单（稳定/低延迟/高速/综合）
python3 export_subs.py          # 生成各格式订阅并逐个反解校验
python3 build_manifest.py --selftest  # 统一清单自测（时间规范化/哈希/可复现）
bash verify.sh                        # P24 一键验证：核心回归、自测、门禁、演练、workflow YAML 与页面 JS
python3 audit_privacy.py              # 公开产物脱敏审计（data/*.json 与页面不许有凭据）
python3 build_manifest.py --write     # 生成统一构建清单
python3 check_consistency.py          # 发布门禁（同轮/哈希/数量异常下降）
python3 drill_publish.py              # 发布失败回滚演练（不改仓库）
python3 screen.py               # 审核候选源（试采集→解析→去重→真实检测）
python3 discover.py --dry-run   # 检索新的候选仓库，只看结果不落盘
python3 score.py --report       # 用现有 stats 重算评分并重写质量报告
python3 lifecycle.py            # 看节点存活统计（跟踪数/近 7 天新增/中位存活）
python3 history.py              # 看节点历史规模与稳定性分布
python3 history.py --trend 14   # 最近 14 天的抽样数/可用率/P50 延迟
python3 history.py --sizetest   # 一万条规模下的文件体积实测
python3 netsafe.py              # 出网边界自测（SSRF/大小/超时/脱敏/原子写，30 项）
python3 restore.py list         # 看数据文件最近改了什么
python3 bench.py                # 规模压测（500/2k/5k/10k，写 docs/P14-bench.md）
python3 drill.py                # 故障演练七项（写 docs/P14-drills.md）
python3 clienttest.py           # 用 Mihomo / sing-box / Xray 真实导入订阅
open index.html                 # 或直接双击
```

`score.py` 依赖 `data/sources_stats.json`（CI 每轮生成）。本地想跑通整条评分链路，
用 `NODES_FORCE_WRITE=1 python3 collector.py`：会强制落盘，并把历史标记为本地环境；
CI 下一轮检测到环境切换会重新积累——本地出口网络的可连率和机房不可比，
混在一起会把「换了个网络」算成「源在变差」。
