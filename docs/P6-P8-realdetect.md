# P6–P8：真实检测、评分分类与订阅输出

> 检测结果每轮重写：`data/nodecheck.json`（原始）、`data/node_scores.json`（评分）、
> `data/subscriptions.json`（订阅清单）。本文的实测数字取自 2026-11-25 04:23 那轮。

## 1. 为什么必须做真实握手

到 P5 为止，页面上所有「可连率」都是 TCP 握手：**端口开着就算通**。

这个指标有它的价值——它便宜、能全量跑、能回答「这个源还活着吗」。但它回答不了
「这条节点能不能用」。一个 vmess 节点完全可能端口开着、uuid 早已失效，或者 TLS
在中间被掐断。用户装了发现一条都不通，而页面写着 83% 可连。

所以 P6 把抽样节点交给 mihomo（vmess/vless/ss/trojan/hysteria2/tuic/anytls 的参考
实现），每个节点绑一个本地 socks 端口，通过它真的去访问 `gstatic/generate_204`。
拿到 204 才算可用，延迟和出口 IP 都从这条真实链路里量。

**同一批源，两个口径差多少**（anaer，本轮）：

| 指标 | 数值 |
|---|---|
| TCP 抽样可连 | 21/24 = 88% |
| 真实握手可用 | 21/90 = 23% |

端口通的比例是真实可用率的三倍多。这就是 P6 存在的全部理由。

## 2. 抽样与预算

全量 1 万节点逐个握手要几小时，Actions 跑不完。所以：

- **每源上限 90 条，总量上限 1,200 条**，固定随机种子（同库同抽样，结果可复现）
- 分层抽样而不是纯随机：小源只有几十条，纯随机可能一条都抽不到，
  「这个源 0% 可用」就成了「没抽到」的假象
- 本轮实际抽样 997 条——有 4 个源本身不足 90 条，加起来不到上限

耗时：997 条约 7 分钟（40 条一批、单批 20 并发、单节点超时 8 秒）。

### 源级：TCP 可连率几乎预测不了真实可用率

同一轮的两组数字（TCP 来自 `data/sources_stats.json`，真实来自 `data/nodecheck.json`）：

| 来源 | TCP 抽样可连 | 真实握手可用 | 落差 |
|---|---:|---:|---:|
| radarhub | 100% | **87%** (78/90) | ×0.87 |
| radarhub·singbox | 100% | **83%** (64/77) | ×0.83 |
| awesome-vpn | 100% | 90% (18/20) | ×0.90 |
| 尔毛子·可连Clash | 92% | 59% (53/90) | ×0.64 |
| bzfq21 | 96% | 33% (30/90) | ×0.34 |
| Barabama | 83% | 36% (32/90) | ×0.43 |
| 尔毛子·V2Ray | 88% | 18% (16/90) | ×0.20 |
| **anaer** | **88%** | **2%** (2/90) | **×0.02** |
| **ALIILAPRO** | **54%** | **3%** (3/90) | ×0.06 |
| v2ray-configs | 42% | 1% (1/90) | ×0.02 |

两头的反差说明问题：

- **radarhub 的两个入口 TCP 100% 可连、真实 83–87%**，是目前最可信的源。
- **anaer TCP 88% 可连、真实只有 2%**。它 2094 条入库节点里，绝大多数是
  「端口开着、但 uuid/密码早已失效」的历史残留。这个源在只测端口的方案里
  排名靠前（P4 给了 B 级 70.5 分），实际上贡献的可用节点是 2 条。
- **ALIILAPRO 54% / 3%** 同理。它独立新增 2562 条全库第一，真能用的不到 3%。

这条结论比任何单个数字都重要：**一个源的价值 = 真实可用条数，不是节点总数，
也不是 TCP 可连率。** P4 的评分里可连率占 40 分，现在看这个权重给错了对象——
它测的是端口，不是节点。

（不立即改 P4 的权重，是因为要先用几轮真实数据确认这个反差是稳定的，
而不是某一轮的偶然。下一轮会把 `真实可用率` 作为独立维度并降权 `TCP 可连率`。）

## 4. 评分

权重照任务书：真实可用性 30 / 延迟 20 / 速度 20 / 多轮稳定性 15 / IP 质量 10 /
流媒体与 AI 5。

两个必须说明的地方：

1. **流媒体与 AI 那 5 分恒为 0**，因为没做那类检测。那需要登录态、地区版权库和
   持续维护的判定规则，做不准就会给出「看起来精确但会过期」的结论。少 5 分比
   编 5 分强，所以总分上限实际是 **95**。
2. **IP 质量是启发式**：按 ISP/ASN 关键词判断机房 IP。标签写「机房 IP」而不是
   「高风险」——黑名单命中、代理库命中这些没有数据源，凭 ASN 下不了那个结论。

等级：S ≥88 / A ≥78 / B ≥65 / C ≥50 / D <50。不可用的节点记 0 分、等级 `—`。

### 尺度改过一次，原因写在下面

第一版把延迟定成「100ms 满分、800ms 归零」，速度定成线性（5MB/s 满分）。
跑出来 340 个可用节点的中位分只有 52.2，`best`（≥65）只有 **8 条**。

这不说明节点差，说明**尺度和现实分布不匹配**：本轮 P50 延迟 675ms，
按第一版只能拿 3 分；速度用线性刻度，让 2MB/s 和 200KB/s 看起来差不多，
而实际体验差十倍。

改成：

| 维度 | 旧 | 新 | 依据 |
|---|---|---|---|
| 延迟 | 100ms 满 / 800ms 零 | 150ms 满 / 1500ms 零 | P50 675、P90 3010，超 1.5s 实际接近不可用 |
| 速度 | 线性，5MB/s 满 | 对数，50KB/s→0、5MB/s→满 | 带宽差异是数量级的，线性刻度会抹平它 |

另外 `--speed` 之前没开，速度 20 分恒为 0，可用节点上限只有 75 分——这本身
就让 `best` 几乎不可能达标。现在对握手成功的节点下载 512KB 测速
（340 条约 170MB 流量、30 秒）。

改完再跑，`best` 才有实际意义。这个调整不是为了「凑数」，是让尺度和
数据的真实分布对上；但确实需要提醒：**任何评分尺度的选择都会改变分组结果，
所以尺度本身必须写下来、可复核。**


## 5. 地区分类

按**真实出口 IP** 分，不用节点名里的国旗。名字是作者自己写的，和实际出口经常
对不上——本轮出口第三名是德国，而节点名里几乎看不到 DE。

分类：香港 / 中国台湾 / 日本 / 新加坡 / 美国 / 韩国 / 欧洲（40 个国家合并）/ 其他。

## 6. 订阅输出

四种格式 × 12 个分组：

| 分组 | 条件 |
|---|---|
| all | 全部（唯一不受真实检测限制的分组） |
| best | 真实可用 且 评分 ≥65 |
| stable | 连续三轮真实可用 |
| lowlat | 可用 且 延迟 <200ms |
| fast | 可用 且 ≥2MB/s |
| hk / tw / jp / sg / us / kr / eu | 按真实出口地区 |

**每种格式生成后立刻用自己的解析器读回来校验条数**，对不上就判失败并写进
`subscriptions.json` 的 `failed`。只改扩展名冒充转换成功，是这类项目最常见
也最难发现的错误。

`streaming` / `ai` 两组没有实现，写进 `not_implemented` 并注明理由，不生成
空文件充数。

## 7. 凭据边界

`export/` 全程 gitignore，只作为 Actions artifact 保留 1 天。订阅文件本身就是
凭据集合——把 `best.txt` 提交到公开仓库，等于把几百个别人的账号挂在网上。
仓库里只有 `data/subscriptions.json`（各分组的条数与文件名，不含任何 URI）。

## 8. 已知限制

- 检测结果是**抽样**，不是全量。页面上「真实握手 90 个 · 可用 21」的 90 是样本量，
  不是这个源的总数。
- 单轮数据波动大。同一个源两轮之间的可用率可能差 10 个百分点以上，这是免费
  节点的常态，不是检测不稳定。
- 不做流媒体/AI 检测，不判断 IP 是否在风控黑名单。
- 出口 IP 来自 ip-api 免费接口，只给国家/城市/ASN/ISP，没有更细的判定。
