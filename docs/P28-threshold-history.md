# P28 门槛评估与历史数据诚实化报告

第二轮审计问题 9（best 65 分门槛）与问题 10（365 天/30 天历史是否真在积累）的核查与整改。

## 一、问题 9：best 65 分门槛评估

### 审计发现（真实数据，非推测）

1. **代码里没有 65 分硬门槛**。`picks.py` 的 best 组条件是：`score 非空 + stability≠poor + now_ok`，然后按分数降序取前 200。所谓"65 门槛"从未实现为过滤条件。
2. **本轮 best 组分数范围 56.7 ~ 90.1**（`threshold_watch.py --report` 实测），最低分 56.7，远低于 65——证明当前 best 里确实混入了低于 65 分的节点，65 门槛不存在。
3. **分数分布**（952 条有评分节点）：≥65 有 144 条（15.1%），≥60 有 172 条（18.1%），≥70 有 78 条（8.2%）。p50=0.0 是因为分母含大量未通过节点（0 分），不代表通过节点的中位分数。
4. **样本普遍不足**：`tries=1` 占 75.8%，测过 >3 次的仅 110 条（11.6%）。在 3/4 节点只测过一次的情况下，65 分门槛缺乏多轮稳定性支撑，现在拍板调整阈值是不负责任的。

### 整改

新增 `threshold_watch.py`：每轮从真实 `node_scores.json` + `picks.json` 追加一行观测到 `data/threshold_watch.json`，记录分位数、各门槛(50/55/60/65/70/75)条数、best 组真实分数范围。CI 每轮自动跑（daily.yml 新增"优选门槛观测"步骤，失败不阻塞发布）。

本轮已写入第 1 个自然日的真实观测：
```
门槛观测：已追加 2026-11-25 14:15，有评分 952 条，≥65 144 条
  覆盖 1/7 天
best 组 200 条，分数范围 56.7 ~ 90.1
结论：未满 7 天，不下阈值结论（本会话无法加速）
```

### 无法在本次会话完成 / 不下结论的部分

**连续 7 天评估本身无法完成**：时间不可压缩，本会话无法等待 7 个自然日。因此：
- 不调整 best 门槛（既不改成 65，也不改成其它值）——没有 7 天数据支撑就不拍板；
- 建立可持续观测机制，让数据自然积累；满 7 天后用 `python3 threshold_watch.py --report` 的 rows 做决策；
- 明确把此项列为**未通过 / 待持续观测**，而非"已验证"。

## 二、问题 10：历史数据是否真在积累

### 审计发现（真实数据）

| 项 | 代码支持（策略上限） | 本轮实际数据 |
|---|---|---|
| `trend.json` | 365 天 | `days` 只有 **1 天**（2026-11-25，rounds=2） |
| `node_history.json` | 30 天 | 4133 条节点，`first` 全部 = 20782（2026-11-25，即今天）；其中 2800 条标记 `migrated:true`（从旧数据迁移），并非多轮真实积累 |

**结论：用户担忧属实**——30 天/365 天是代码支持能力，不是仓库里已有的历史。把"代码支持 365 天"当成"已有 365 天数据"是错误的。

### 整改

1. README 历史表增加"窗口上限（代码策略）"与"当前实际已积累"两列，明确写出 trend 仅 1 天、history 尚未形成跨轮历史、多数为迁移记录。
2. 增加说明："窗口是上限不是已拥有多少历史；实际天数以文件内真实数据为准，`history.py --report` / `threshold_watch.py --report` 按真实数据报天数"。
3. 页面已有的诚实降级（跟踪不足 7 天时显示"已跟踪 N 天"而非"近 7 天新增"）予以保留，不改。
4. `threshold_watch.json` 纳入观测，7 天评估同样按真实天数报，不伪造。

### 观测身份与重跑幂等（P24 续审）

`ts` 来自评分数据，只有分钟精度，因此只用于时间顺序/自然日覆盖统计，不作为观测身份。同一 `ts` 下不同输入快照可以各自保留。新行的 `snapshot_id` 是 `node_scores.json` 与 `picks.json` 原始文件内容的 SHA-256 组合指纹；相同输入指纹无论相邻与否都只追加一次。`distinct_days` 仍只按 `ts` 的日期部分计数。

既有行没有输入指纹，保持原样且不回退匹配；因此若首次重放与旧行相同的快照，可能追加一行，新行之后的相同输入重跑则由指纹去重。此策略优先保留无法由旧数据证明为重复的观测，不因相同时间戳或相同汇总值合并历史。
