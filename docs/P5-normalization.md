# P5：解析标准化与异常隔离

> 本文是阶段性设计与实测记录，数字取自 2026-11-25 的一次完整采集。
> 隔离区的逐轮数字在 `data/quarantine.json`，由 `collector.py` 每轮覆盖。

P1 已经做过「多格式解析 + 全参数指纹去重」，所以 P5 真正剩下的是三件事：
冷门协议、异常配置隔离区、首次/最近发现时间。三件都做完了，其中两件翻出了
以前静默丢失的数据。

## 1. 协议支持

| 协议 | URI | Clash | sing-box | 入 库 |
|---|:--:|:--:|:--:|:--:|
| VMess / VLESS / Shadowsocks / Trojan | ✅ | ✅ | ✅ | ✅ |
| Hysteria2 | ✅ | ✅ | ✅ | ✅ |
| TUIC | ✅ | ✅ | ✅ | ✅ |
| SOCKS5 | ✅ | ✅ | — | ✅ |
| **AnyTLS** | ✅ | ✅ | ✅ | ✅ |
| HTTP / HTTPS | ✅ | ✅ | ✅ | ❌ 见下 |
| Hysteria v1 / Snell / SSR | — | — | — | ❌ 见下 |

**AnyTLS 是这轮新增的**。它只在 TLS 上叠一层自适应填充，参数只有 sni / 证书校验 /
uTLS 指纹，解析成本很低，但以前完全不被识别——库里 0 条。补上后入库 30 条。
它的 `insecure`（跳过证书校验）会被写进指纹：两台机器同一个密码、只有
`skip-cert-verify` 不同，安全性完全不同，不该合并成一条。

**明文 HTTP 不入库，但也不静默丢弃**。理由很直接：跨境链路上用户名密码和全部流量
明文可读，这类条目还大多是带广告的公开代理池。但它会进隔离区并计入统计——本轮
768 条，其中 Barabama 一个源就有 599 条。以前这些条目是在 `_clash_one` 里
`return None` 掉的，图上表现为「这个源声明 1383 条、解析 1383 条」，而实际上
有 599 条根本没进库。这个数字对不上，但页面上看不出来。

**Hysteria v1 / Snell / SSR 仍然不支持**。不是漏了：sing-box 已移除 v1 支持，
主流客户端也不认；Snell 是 Surge 私有协议；SSR 协议早已停止维护。本轮合计 6 条，
进隔离区留痕，不写解析器。

## 2. 异常配置隔离区

以前被丢弃的条目是「消失」，现在是「消失 + 有记录」。`data/quarantine.json`
按原因汇总，每源最多抽 5 条样本：

| 原因 | 本轮条数 | 说明 |
|---|---:|---|
| 明文代理 | 768 | 主动不收录，理由见上 |
| 非公网地址 | 55 | 127.0.0.1、10.x、192.0.2.x（RFC5737 保留段） |
| 条目结构异常 | 30 | 不是对象、字段类型不对（端口写成字符串等） |
| 不支持的协议 | 6 | Hysteria v1 / Snell 等 |
| 缺少地址或端口 | 1 | — |
| **合计** | **860** | 占声明总量 5.5% |

**这个文件不含凭据**——只记协议、节点名、地址、端口、原因。它要提交进公开仓库，
把原始订阅行搬进去等于换个文件继续公开托管别人的账号。代码里
`_reject_of()` 是唯一的写入口，就是为了让这件事只有一处可改。

另一个用途：`screen.py` 审核候选源时也会带上 `quarantined` 计数，这样
「声明 2000、解析 1200」这种差额在审核阶段就能解释，不用靠猜。

## 3. 首次 / 最近发现时间

`lifecycle.py` 按天记每个指纹的 `[首次, 最近]`，派生两个指标：

- **近 7 天新增 N**（卡片上）：这个源还在产新节点吗
- **中位存活天数**（悬浮提示）：拿到的节点大概能活多久

为什么要这两个：总量大不代表还在更新。一个源可能只是旧节点被到处转发，连续几周
零新增，实际早就停更了——但它的条数看起来一直很健康。反过来，一个条数不多的源
如果每周稳定产出新节点，反而更值得用。

设计上的几个取舍：

1. **按天不按小时**。每 3 小时采一轮，存小时会让文件大三倍，而「存活 12 天」比
   「存活 12 天 3 小时」有用。
2. **指纹截断到 16 位**（64 bit）。一万个节点撞车概率约 3e-12，实际为 0，
   但每条记录省 16 字节，文件从 515 KB 降到 339 KB。
3. **45 天没再出现就清掉**。留太久只会让文件无限增长，而且隔 45 天又冒出来的
   节点，按新节点算才合理。
4. **「回归」判定用 `last < today - 1`**，不是 `last < today`。后者会把每一条
   跨天连续出现的节点都算成「断档后回归」——第一版就是这么错的，
   自测里 `back` 从 0 变成 1 才发现。

### 冷启动不能报「新增」

第一轮建库时所有节点都是「首次见到」，直接显示「近 7 天新增 10519」是假信息：
它说明的是我们刚开始记录，不是源在产新节点。更糟的是它会和「源 3 天没更新，
可能已停更」并排出现，两句话互相打脸。

所以页面在跟踪跨度不足 7 天时显示 **「已跟踪 N 天」**，满 7 天后自动切成新增数。
这个 `life_span` 跟着 `nodes.json` 走，不靠前端算日期。

## 4. 顺带修掉的一个解析 bug

`parse_any()` 对 `bytes` 入参会 `strip()`，对 `str` 入参不会。结果是一个开头有
空行的 sing-box JSON 会走不进 `text[:1] == "{"` 分支，一路掉到「逐行 URI」，
整份文件解析成 0 条。线上走的是 `bytes`（`fetch()` 返回 bytes），所以一直没暴露；
本地拿字符串调试时才踩到。改成两种入参都 strip。

## 5. 已知边界

- **不动源文件**。解析只为统计与去重，不回写、不合并、不改写原始链接。
- **隔离区只抽样**。每源 5 条，`samples` 上限 300 条——它的用途是「看一眼为什么少了」，
  不是全量留档。
- **存活天数是观测值，不是预测**。一个节点「已存活 30 天」不代表它明天还通，
  只代表它过去 30 天一直在源里出现。
