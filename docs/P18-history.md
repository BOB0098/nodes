# P18 节点历史与智能优选

P17 把「评分依据」从 TCP 端口换成真实握手。P18 解决下一个问题：
**一次检测只能说明「此刻能不能用」，说明不了「一直靠不靠得住」。**

检测是抽样的：每轮抽 1,200 条 / 9,846 条。一条节点可能这一轮通、下一轮没抽到、
第三轮抽到又不通。没有跨轮记录，这三种情况在页面上长得一模一样。

---

## 1. 三个文件，各管一件事

| 文件 | 内容 | 窗口 | 体积 |
|---|---|---|---|
| `data/node_history.json` | 逐节点：首次/最近出现、最近成功、累计测/通次数、连续成功失败、六时段成功率、最近 5 次延迟、最近 3 次速度 | 30 天 | ~1.3 MB（1 万条） |
| `data/trend.json` | 日级聚合：当天轮次、抽样数、可用数、P50 延迟、新增/消失、按协议分桶 | 365 天 | ~146 KB（一年） |
| `data/picks.json` | 四类榜单成员与顺序 + 排序依据说明 | 每轮重写 | ~120 KB |

旧文件 `node_score_history.json` 已并入 `node_history.json` 并移除。它只有
`{ok_streak, fail_streak, last_ok(bool), checked}`——**`last_ok` 是布尔不是日期**，
所以「最近一次成功是哪天」根本答不了。这正是 P18 要重做的直接原因。

日趋势为什么单独存：7 天/30 天曲线如果每次从逐节点历史重算，要读一万条记录、
遍历每条的日期字段。一天一行之后，画图是读 30 个对象。

## 2. 稳定性：从「连续轮次」改成「累计成功率」

### 旧口径是错的，而且错得很隐蔽

旧代码：

```python
ok_streak >= 3  →  标签「稳定」
```

看起来合理（连续三轮都能用），但抽样率只有 12%。一条节点每轮被抽中的概率 0.12，
连续三轮都被抽中**并且**都成功 ≈ 1.7‰。真正稳定的节点也几乎拿不到这个标签。

实测（2,800 条有记录的节点）：

| 口径 | 「稳定」条数 | 问题 |
|---|---:|---|
| 旧：连续 3 轮成功 | 342 | 其中大量只测过 3 次，一次偶然全中就算稳定 |
| 新：测过 ≥3 次且成功率 ≥80% | **90** | 要求有足够样本，且整体表现好 |

少掉的 252 条，绝大多数是「3 次全中但只测过 3 次」或「最近 3 次中但历史成功率不到 80%」。
后者尤其重要：一个 8 次里成功 5 次的节点，最近 3 次恰好都中，旧口径叫它稳定，
新口径算 62.5% 归入「一般」。用户装进客户端之后遇到的那 3 次失败，旧口径从来没告诉过他。

### 顺带修掉一个迁移缺陷

旧记录里 `ever_ok` 是后加的布尔字段，早期记录没有它。实测 2,800 条里有 **152 条**
`ok_streak > 0` 却 `ever_ok == False`——明明刚成功过，却被判成「从未成功」，
标成「待复测」而不是「不稳定」。

现在不看这个字段，直接看 `hits`（累计成功次数）。迁移时 `hits` 从 `ok_streak` 反推，
标 `migrated: true`，**前 6 次不给「稳定」**——因为那是下界估计不是真实计数。
样本攒够 6 次，估算值占比降到一半以下，才允许参与正常判定。

### 四档定义

| 等级 | 条件 | 页面文案 |
|---|---|---|
| `stable` | 测过 ≥3 次 且 成功率 ≥80% 且 没有连续 2 次失败 | 稳定（5/6 次成功） |
| `fair` | 测过 ≥3 次 且 成功率 50–80% | 一般（3/6 次成功） |
| `poor` | 测过 ≥3 次 且 成功率 <50%，或连续失败 ≥2 次 | 连败 3 次（历史 5/6） |
| `unknown` | 测过 <3 次，或迁移数据未满 6 次 | 仅测 2 次 |

`unknown` 不是「差」，是「还没有证据」。评分里它拿 5/15 分（不是 0）——
测过一次就成功，不足以证明稳定，但也不该比从没测过还低。

## 3. 抽样偏差：覆盖度优先

每轮 1,200 条 / 9,846 条 = 12%。纯随机抽 8 轮，覆盖率是
`1 - (1-0.12)^8 ≈ 64%`；一个节点要攒到「测过 3 次」平均需要 25 轮 ≈ 三天。

改成**同源内优先抽测得少的**之后，前 8 轮基本把全库走一遍，之后才开始重复。
同样预算，稳定标签的判定提前约两倍。

```python
arr = sorted(arr, key=lambda n: tries.get(fp[:16], 0))
```

`rnd.shuffle` 先打散，`sorted` 是稳定排序，所以同 `tries` 的节点之间仍随机，
且种子固定 → **同一轮同一种子抽出的结果完全可复现**（`nodecheck.py --selftest` 有断言）。

### 仍然存在的偏差：大源覆盖慢

每源配额 90 条。小源（几十条）一轮就全覆盖；大源 `anaer` 1,759 条，
要 20 轮 ≈ 2.5 天才能扫一遍。所以大源的「稳定」条数天然偏少，
这不是算法问题，是「每轮只跑 1,200 条」的预算问题。写在这，不改。

## 4. 四类榜单

`picks.py` 输出 `data/picks.json`，每类都带 `basis`（规则 + 排序依据），页面直接显示。

| 榜单 | 入选条件 | 排序 | 当前条数 |
|---|---|---|---:|
| 稳定 | 测过 ≥3 次、成功率 ≥80%、无连败 | 成功率 ↓ → 测试次数 ↓ → 延迟 ↑ | 90 |
| 低延迟 | 中位延迟 ≤300ms、测过 ≥2 次 | 延迟 ↑ → 成功率 ↓ | 67 |
| 高速 | 中位速度 ≥1MB/s、测过 ≥2 次 | 速度 ↓ → 成功率 ↓ | 53 |
| 综合质量 | 本轮通过、不在连败中 | 评分 ↓ → 成功率 ↓ | 200（符合 316） |

三个刻意的设计：

1. **候选池 = 本轮实测通过 ∪ 历史成功率 ≥90% 且 7 天内成功过**。
   只用本轮结果会让榜单只剩 300 条（12% 抽样 × 35% 通过率），
   历史候选的每条结果标 `src: "history"`，延迟/速度取历史中位数，页面必须能区分。
2. **缺失数据不伪装成零**。没有延迟记录的不进低延迟榜（不是记 0ms 排第一），
   没有测速的不进高速榜。`bps` 在 JSON 里是 `null` 不是 `0`。
3. **所有排序键最后都用 `fp` 兜底**。同分同延迟时顺序必须稳定，
   否则两次刷新榜单顺序变了，用户会以为数据在乱跳。

`counts` 是**实际输出**的条数（订阅按它对账），`matched` 是符合条件的总数。
综合榜符合 316 条但只输出 200 条，只写一个数就会出现「榜单说 316、订阅 200」，
一致性检查必然报错——所以两个数分开记。

### 榜单与订阅同一个来源

订阅的 `best / stable / lowlat / fast` 四组**直接读 `picks.json` 的成员和顺序**，
不再自己筛一遍。以前两套筛选各自为政，会出现「页面上排第一的节点不在订阅第一行」。
现在订阅里的第一行就是榜单第一行。

`check_consistency.py` 新增第 6 项：榜单四组条数必须等于订阅四组条数，不等就阻止发布。

## 5. 体积：实测，不是估算

「一万节点会不会把仓库撑爆」这种问题，估算的答案从来不可信。所以跑了两组实测。

### 单文件大小

```bash
python3 history.py --sizetest 12000
```

```
体积测试：12000 条 / 6 次观测
  序列化 1609 KB，均 137 字节/条
  死号 4178 条，均 77 字节；活号均 170 字节
```

落盘前会去掉默认值字段（`"last_ok":null,"hits":0,"ms":[],"bps":[]` 这类），
死号从 150 字节压到 77 字节。真实库 9,846 条约 **1.3 MB**。

上限线设在**单文件 2 MB、条目 15,000**，超出说明窗口或抽样出了问题。

### Git 增长

建了一个空仓库，把 1 万条规模的历史文件提交一次，然后模拟 20 轮演化（每轮改约 1,200 条）并提交：

| 指标 | 数值 |
|---|---:|
| 20 轮后 `.git`（未 gc） | 6,496 KB |
| `git gc --aggressive` 后 | **812 KB** |
| 折合每轮 | 约 35 KB |

未 gc 的 loose objects 会吓人（每轮约 317 KB），但 GitHub 会定期 gc，
打包后相近版本之间的 delta 压缩非常有效——这个文件每轮只改几百个字段，
不是整份重写。按 35 KB/轮 × 8 轮/天算，**一年约 100 MB**（含其他数据文件）。

## 6. 验收测试

原任务书列出的六类历史场景都做成了 `history.py --selftest` 的断言，不靠人眼检查：

日趋势的 P50 是当天所有成功延迟样本合并后的中位数，不是最后一轮的 P50，也不是各轮 P50 再取中位数。实现只在当前日保留延迟值频次表；日期切换后保留最终 P50 并丢弃频次表。旧版 trend 行只有 P50、没有原始样本，无法精确还原分布，因此不合成样本或改写旧 P50。该口径的专项边界由 `tests/test_history_daily_p50.py` 覆盖，并接入 `verify.sh`。

| 场景 | 断言 | 结果 |
|---|---|---|
| 节点新增 | 首次观测建立记录、时段桶记「全成」 | ✔ |
| 连续成功 | 4/4 成功 → `stable`；延迟中位数正确 | ✔ |
| 样本不足 | 只测 1 次 → `unknown`，不给稳定标签 | ✔ |
| 连续失败 | 连败 3 次 → `poor`，`fail_run` 累加 | ✔ |
| 失败后恢复 | `fail_run` 清零、`ok_run` 重新计、累计次数不清零 | ✔ |
| 节点消失 | 超 30 天窗口被裁剪，裁剪条数正确返回 | ✔ |
| 改配置 | 新指纹独立建账，旧记录一个字节都不变 | ✔ |
| 断档回归 | 隔 5 天回来记 `revived`；连续两天不记 | ✔ |
| 分时段 | 同段一成一败 → `2`（部分），`slot_ok` 统计正确 | ✔ |
| 日趋势 | 同日两轮累计、P50 合并原始样本、空样本不覆盖、`gone` 取最大值不累加、365 行上限 | ✔ |
| 旧数据迁移 | `hits` 从 `ok_streak` 反推、标 `migrated`、样本不足归 `unknown` | ✔ |
| 落盘压缩 | 空字段省略后，稳定性/时段判定结果不变 | ✔ |
| 体积上限 | 12,000 条 < 2 MB | ✔ 1,609 KB |
| 排序可复现 | 同输入两次构建顺序一致；三条全等数据按 `fp` 排序 | ✔ |

## 7. 已知限制

1. **迁移数据的成功率是下界不是真值。** 旧记录没存 `hits`，只能从 `ok_streak` 反推。
   这些记录前 6 次不给 `stable`，等新数据稀释。跑三轮（约 9 小时）之后
   才会出现「全部基于真实计数」的稳定标签。
2. **大源覆盖慢。** 每源 90 条配额，`anaer` 1,759 条要 20 轮才扫一遍。
3. **六时段成功率需要跨天累积。** 迁移记录的 `slots` 全是 `0`（旧数据没有这个概念），
   中位「测过 0 段」是正常的，要 6 段各跑过一轮才有意义。
4. **改配置识别只做「不错配」，不做「合并」。** 同一节点换 IP 会被记成新指纹，
   历史从零开始。合并需要判定阈值，误合并会把两个真实节点算成一个——
   宁可多算，不肯错并。
5. **速度只测部分节点。** `nodecheck.py` 只对延迟 <1500ms 的节点测速（省时间），
   所以「高速」榜的候选天然比「低延迟」榜少。
6. **趋势图还没上页面。** `trend.json` 只到数据层，可视化留给 P21。
   现在只能 `python3 history.py --trend 14` 在终端看。
