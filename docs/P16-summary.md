## 1. 一句话

## 3. 优化整改，按「用户能感知到什么」分

### 3.1 从「能连」到「真能用」

这是整轮里唯一称得上改变性质的一件事。

以前的「可连率」是 TCP 握手：端口开着就算通。实测下来这个指标会说谎——
`anaer` 端口 88% 可连，真实握手 **2%**；`ALIILAPRO` 54% / **3%**。
端口通的比例是真实可用率的三倍以上。

现在每个抽样节点绑一个本地 socks 端口，经 mihomo 访问 `generate_204`，拿到 204 才算数，
延迟和出口 IP 都从这条真实链路里量。`best` 订阅只收这一口径下通过的节点，**220 条**。
宁可给 220 条能用的，也不给 9,846 条看着多的。

代价写在明处：全量一万条要 45 分钟，所以每源 90 条、总量 1,200 条封顶，
按天换随机种子，一周覆盖全库。

### 3.2 数据本身可信

- **去重改成全参数指纹**（27 个字段，截断 16 位 hex）。按地址比对两头都会错：
  同机不同 UUID 是两个节点，同 UUID 换域名是一个节点。
- **四类载体统一解析**。同一个节点在 Clash YAML 和 sing-box JSON 里的字段名完全不同，
  以前只认 YAML，等于把另外三类源全扔了。
- **三个真 bug**，都是客户端实测逼出来的，不是读代码看出来的：
  1. `reality-opts` 空 dict 被当成「这是 reality 节点」——`p.get("reality-opts") or {}`
     后面跟 `isinstance(dict)` 判断，空 dict 也过。影响 2,374 条误标、1,987 条公钥为空，
     sing-box 直接拒绝整份配置。
  2. 非法 UUID（节点名被写进了 id 字段，如 `monacoVPN`、`@Geek_Spot`）入库，
     Xray 报 `invalid byte: U+0078 'x'`。隔离 359 条。
  3. `network` 字段被上游的 emoji 污染（`ws#🍪...`），Xray 报
     `unknown transport protocol`。加了白名单归一。

### 3.3 不出事

| 机制 | 挡的是什么 |
|---|---|
| 出网四道闸（协议白名单 / 解析结果逐个比对公网 / 3 跳重定向每跳重查 / 12MB + 90s 预算） | 源被投毒指向内网、无限重定向、坏源撑爆内存 |
| 日志脱敏 | `HTTPError.__str__()` 就是完整 URL，订阅 query 常带 token，而 Actions 日志公开可读 |
| 检测回归闸门（本轮可用 < 上轮 40% 且上轮 ≥200 条 → 不覆盖，退出码 3） | mihomo 下到坏包、机房出口限速这类「让所有节点看起来都死了」的事故 |
| 原子写（临时文件 + `os.replace`） | 中断留下半截 JSON，下一轮整页空白 |
| `restore.py list/diff/to/undo` | 数据坏了能回到任意一轮，且不连带回滚代码 |

### 3.4 交付与验证

- **Docker 一条命令跑完一轮**，容器里真跑过才发现两个问题（漏 `template.html`、
  缓存目录定在容器根目录只读），都已修。
- **压测**：9,846 条离线全链路 18.6 秒 / 峰值 336MB；联网 2,000 条 555 秒 / 107MB。
  规模涨 19.7 倍、耗时涨 22.2 倍，没有超线性点。
- **七项故障演练**：真 404、真 `kill -9`、真 `SIGSTOP`、真把 mihomo 换成 `sleep`。
  演练第一次就把「检测失败直接覆盖结果」逼出来了。
- **客户端真实导入**：Mihomo 12/12、sing-box 12/12、Xray 全量 `Configuration OK`。
  Xray 26 收紧策略后拒掉的那几类（明文 vless/trojan、`allowInsecure`、h2 传输、
  旧 ss 加密、reality+ws）逐类计数，不假装通过。

### 3.5 页面

订阅入口和 Pages 路径**没动**，这是任务书的硬约束。改的是展示层：
把「端口可连」和「真实可用」放进同一个视口，避免拿 83% 当卖点；
时间戳统一东八区（之前页头写「07:17 更新」、总览写「检测于 23:32」，同屏两个时区）。

## 4. 九个坑里，五个是跑出来的

| 问题 | 影响 | 怎么发现的 |
|---|---|---|
| `reality-opts` 空 dict 误判 | 2,374 条误标，sing-box 拒整份订阅 | 客户端实测 |
| 检测失败直接覆盖 `nodecheck.json` | 一次抖动抹掉上轮 340 条结论 | 故障演练 |
| `urlopen().read()` 无上限 | 一个坏源吃光 runner 内存，表现成「今天没更新」 | 代码审计 |
| 非法 UUID 入库 | 359 条 100% 连不上的节点白占检测配额 | 客户端实测 |
| hysteria2/tuic/anytls 缺 TLS 块 | sing-box `TLS required`，整份被拒 | 客户端实测 |
| `network` 被 emoji 污染 | Xray `unknown transport protocol` | 客户端实测 |
| 日志打完整 URL | 订阅 token 进公开日志 | 代码审计 |
| 非原子写 | 中断留半截 JSON，整页空白 | 故障演练 |
| 单源无总预算 | 半死的源把采集拖到 workflow 超时 | 演练第 1 项跑了 46 秒才暴露 |

另外有两条工程细节，不写下来下次还会踩：

- **`if "$@"; then … fi` 之后取 `$?` 恒为 0**（拿的是 if 语句自己的返回值）。
  采集崩了脚本还打印「失败（rc=0）」。改成先 `$@` 再 `rc=$?`。
- **`ru_maxrss` 是进程生命周期峰值**，同一进程连跑四档会互相污染，
  所以压测每档开独立子进程。

### 一次被数据打脸的推断

修 reality 误标时顺手把它写成了 `anaer` 可用率低的原因：那个源 90 条只通 2 条，
而它 1,796 条里 1,450 条被误标。时间挨着、量级对得上，看起来完全成立。

修完再跑，`anaer` 还是 **0/90**。原因是 mihomo 对「reality 但没公钥」会当普通 TLS
处理，照样能连——误标真正伤的是 sing-box 和页面标注，不是握手。`anaer` 连不上
是它节点本身就这样。

这条留在这里，因为它正是本项目一直在防的错误：**改完一个 bug，顺手给它记一份功劳。**

## 5. 不足

分三层：会误导结论的、知道不做但该说清的、该做还没做的。

### 第一层：会误导结论的（建议优先处理）

**① 源评分的权重给错了对象，`anaer` 现在拿 A 级。**

可连率占 40 分，而它测的是 TCP 端口，不是节点能不能用。后果是：

| 来源 | TCP 可连 | 真实握手 | 源评分 | 实际贡献 |
|---|---:|---:|---|---|
| anaer | 88% | **2%** | **A 87.0** | 1,759 条里几乎全是死号 |
| Pawdroid | 100% | 5 条全重复 | **B 73.0** | 0 条独立新增 |
| radarhub | 100% | 83–87% | **B 74.8** | 全库最可信的源之一 |

（TCP 与真实握手是同一轮的配对值，取 `docs/P6-P8-realdetect.md` 记录的那轮；
源评分取 11-25 07:37 最新一轮。两列不同轮但同一口径。）

最高 91.7、最低 73.0，跨 **18.7 分**；等级表五档（S/A/B/C/D）实际只用到三档
（1/9/5/0/0），连一个 5 条、100% 重复的源都能拿 73 分 B 级——因为「稳定性 18 分
+ 合规 6 分」几乎是保底白送。

这不是没人发现：`docs/P6-P8-realdetect.md` 第 3 节已经写明「可连率 40 分给错了对象，
下一轮会改」。**到现在还没改**，理由是要先确认这个反差是稳定的、不是某一轮的偶然。
现在两轮数据（34.2% / 34.5%）都在同一量级，理由已经不成立了——这是最该补的一条：
把「真实可用率」提为独立维度（建议 30 分），TCP 可连率降到 10 分只作存活性判断。

**② 失败原因只有一个标签，卡住所有归因。**

`nodecheck.py` 的 `probe()` 只读 `%{http_code}`，连不上就记 `HTTP 000`。
最新一轮 609 条失败**全是这一个值**。而 `000` 至少混了四种情况：
DNS 解析失败、TCP 拒绝、TLS 握手失败、超时。

后果很实际：分不清「源发了坏节点」和「机房出口在掐这类流量」，
也就没法回答「为什么这个源这轮掉了 20 个百分点」。

改法很轻：curl 的 `returncode` 本来就区分 6/7/28/35/56，加一行映射即可，
`--max-time` 那支的「超时」已经有单独分支，说明作者当时意识到了、只是没铺开。

### 第二层：知道不做，但要说清边界

**③ 流媒体 / AI 解锁不检测。** 评分里那 5 分恒为 0，总分上限 95。
需要登录态、地区版权库和持续维护的判定规则，做不准就会给出「看着精确但会过期」的结论。
少 5 分比编 5 分强，但页面上不能让人以为「95 是满分」。

**④ 没做过「一万条同时握手」。** 只有分层抽样（930–1,200 条）+ 20 并发。
联网压测到 2,000 条（555 秒 / 107MB），没有再往上。
所以「1 万条节点的真实可用率」是抽样外推，不是实测。

**⑤ Hiddify 只验证了配置格式，没做 GUI 导入。** 它没有免登录 CLI，
`docs/P15-clients.md` 里如实标了「未做」，没有拿格式校验冒充导入成功。

**⑥ 三个免费云平台都不能认定为「适合长期常驻」。** InstaBox 空闲 30 分钟自动暂停、
单次上限 120 分钟；Altare 免费 4 台共享 6GB，回收策略没写；Nodaroo 只有 Discord 登录页、
没有 Docker 文档——证据不足，不猜。

### 第三层：安全与运维的残余

**⑦ DNS rebinding 的 TOCTOU 窗口没堵死。** 校验收到的 IP 是公网，但真正建连时
会再解析一次，中间有窗口。前提是源清单可信——能让 DNS 指向内网的人已经有仓库写权限。
`docs/P13-security.md` 写了取舍过程，没掩饰。

**⑧ 出口 IP 归属靠 `ip-api.com` 免费额度**（45 次/分钟），不重试不缓存，
失败就记 `cc=null`。最新一轮 33 条连上了但没有地区，归入「未知」。
影响的是地区分组（hk/us/jp 这些订阅）的完整度，不影响可用性判断。

**⑨ 令牌还没撤。** 当初约定「项目迭代完再撤」，现在迭代完了。

## 6. 如果继续做，顺序

1. **改源评分权重**（①）——现在页面在给 `anaer` 打 A 级，这是唯一还在主动误导人的地方。
2. **失败原因分类**（②）——半天工作量，之后所有「为什么掉」的问题才有答案。
3. 把 `failed` 里的错误码也接进 `sources_stats.json`，让源降级有据可依。
4. 视需要做 `best` 订阅的质量回访：220 条里一周后还活着几条——这是唯一能验证
   「真实检测」本身准不准的办法。

前两条做完，这个项目的结论才从「我们测得很细」变成「我们的判断是对的」。
